# 2026.280.2136 — feat(nodejs): assert the pnpm pin <-> allowBuilds key-form coupling (#5)

## Summary

`opencharly/layer-nodejs#5`. The pinned `PNPM_VERSION` and a consumer's `allowBuilds` KEY FORM
are a **coupled pair**, and the coupling was invisible from this repo: the pin lived here, the
key form lived in the consumer (`pod-dsh`), and nothing asserted they agree. A wrong pair
hard-fails the consumer's `dsh-web` profile install at **image build** time.

The rule is now declared beside the pin and **asserted by the candy's own check**, which is this
repo's functional evidence.

- `PNPM_ALLOWBUILDS_GIT_KEY_FORM`, `PNPM_ALLOWBUILDS_PROBED_BARE` and
  `PNPM_ALLOWBUILDS_PROBED_URL` join `PNPM_VERSION` in `var:`, with the measured matrix in the
  comment.
- One new `check:` step asserts the pin, the form and the probes agree. A bump across the band
  now goes **RED on this repo** instead of hard-failing a consumer's build. It accepts only the
  two versions that were MEASURED: any other pin fails loudly and asks the author to re-measure
  and record — the band boundary is deliberately **not** extrapolated from two endpoints.
- The `nodejs-skill:` body mirrors the rule, because the skill entity is the corpus projection
  source (this repo's own rule: a behaviour change not mirrored in the skill leaves the corpus
  stale).

Declared values, quoted from `var:` in this head:

```
PNPM_VERSION: 10.33.4
PNPM_ALLOWBUILDS_GIT_KEY_FORM: bare
PNPM_ALLOWBUILDS_PROBED_BARE: 10.33.4
PNPM_ALLOWBUILDS_PROBED_URL: 10.34.6
```

**Correction to the first revision of this PR (the previous head `bd28408`).** That revision
shipped the check with JavaScript template literals (`${version}`, `${form}`, `${want}`) inside
its `command:`, and its comment claimed "No `${...}` anywhere". Both were wrong. A check step's
command goes through charly's variable substitution, which reads `${X}` as a charly variable and
**SKIPS the step** when it cannot resolve one; `version`/`form`/`want` are not declared charly
vars, so the step would have been a **silent no-op** — disabling the very assertion this change
adds, which is the exact class it exists to prevent. The reviewer caught it. The fix is in the
new head: the messages are built by string **concatenation**, and the command now contains no `$`
character at all, so the substitution path has no token to act on and the step cannot be skipped.
The comment states the rule and the grep that proves it.

The check is extracted from the committed entity and executed with exactly the `var:` values

```
$ cat /tmp/hb-extract.sh

The `grep -c '$'` returning **0** is the point of the correction above: the shipped command
carries no substitution token, so the `${...}`-skips-the-step failure mode is eliminated by
construction rather than argued. `grep` exits 1 on zero matches, which is expected here.

The check is **falsifiable**: it was executed twice more with one drift each, and each fails with
its own message and exit 1:

```

That covers both polarities of the pair (the pin moving and the form moving) and both shapes of
drift (an unmeasured pin, and a measured pin paired with the wrong form).

build (the `dsh-web` profile install, e.g. the `check-dsh-pod` bed in `pod-dsh`), which cannot be

advance to a **merged** ref (Policy B). The step was therefore executed as the runner executes it
— the whole `command:` block, verbatim, under `bash` with the `var:` values exported as ENV — but
NOT through a container build of a consuming image, and I am not claiming otherwise. The follow-on
is the standard producer sequence: this PR merges and `tag-on-merge` mints the CalVer tag, then the
marketplace corpus is regenerated from the new tag (`layer-nodejs` refs bump) and the umbrella's
`marketplace` gitlink advances. Until then the projected corpus carries the OLDER, still-true
skill body — that is the designed behaviour of the corpus, not a divergence.
